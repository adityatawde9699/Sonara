# Architecture

## Current prototype

`sonara.py` is a local command-line orchestrator. It invokes Poppler's `pdftotext -bbox-layout` and parses the result into the versioned `Document`/`DocumentBlock` representation in `document.py`. Blocks carry a stable extraction ID, order, heuristic kind and kind source, source page, and PDF-point bounding box. Extraction notes flag side-by-side regions, repeated blocks, line-end hyphenation, and pages without selectable text. The old `extract_pdf()` text API remains as a compatibility view over the ordered blocks. The default Python Piper path builds a deterministic narration plan and feeds paragraph-sized units to a persistent Piper worker. Sentences within an extracted paragraph stay together; unusually long blocks are bounded at sentence or whitespace boundaries. Piper returns audio sentence by sentence. The worker trims each sentence's built-in edge silence and inserts a per-voice pause (200 ms, or 230 ms for the slower voices) between those internal sentence chunks, with no trailing pause. Sonara adds the longer structure-aware pause after the passage, scaled per voice. Every chunk is then finished by `audio_processing.py` before caching: edge silence is trimmed to short pads, gated speech level is matched to −18 dBFS with a −1 dBFS peak ceiling, and short fades are applied. The worker loads the model once, receives text over a private local stdin protocol, writes PCM WAV chunks to temporary files, and never receives document text in its process arguments. A bounded producer queue exposes chunks as they finish; Sonara persists each completed chunk under `chunks/<document-hash>/<run-id>/`, combines them into `speech.wav` unless `--no-combined-audio` is given (the desktop app passes it), and rewrites source-span metadata to `audio_chunks.json` after every passage. Playback belongs to the desktop app; the CLI's standalone HTML player was removed in 2.0. An explicit `--piper` executable override retains the compatible CLI path and writes text to a temporary file passed by path. No document text is sent over a network.

The process boundaries are intentionally simple: the Python process owns subprocess lifetimes and temporary input files; Poppler decodes PDFs while local Python adapters extract TXT/TEXT, Markdown, DOCX, and EPUB; Piper owns model loading and synthesis; the frontend owns playback. Failures and stderr are surfaced to the user. Source documents are never modified.

`narration.py` now provides a deterministic, standalone planning API over schema-v1 document blocks. It creates paragraph-sized units that carry the original block ID and exact exclusive character offsets. Sentence boundaries are used to group natural passages, not to create one audio chunk per sentence. Concatenating a block's unit source spans reproduces its source text exactly. The spoken layer collapses safe whitespace, but the source field remains unchanged; line-end hyphen breaks are retained. Headings remain whole units. Other blocks use punctuation boundaries, a finite English abbreviation set, decimal and URL/email protection, and common quote-attribution handling. Passages are capped at 1,200 characters or 180 words when a block is unusually long. English rules rewrite `spoken_text` only. They expand titles, reference abbreviations, measurement units and a small pronunciation lexicon, plus years, decades and number ranges where context makes them clear. They also read currency, times, fractions and Roman numerals after counting words or regnal names. ISO dates and numeric bracket citations require explicit opt-in. Transformation records preserve original substrings and offsets, and explicit pronunciation overrides take precedence. The Tauri app exposes a bounded preview of original and spoken text before reading. Unsupported languages retain their text apart from safe whitespace normalization. Unit labels and pause milliseconds are heuristics, not TTS prosody commands. Unmatched and overlapping explicit overrides are rejected.

Passage pauses are derived from punctuation, block type, and block boundaries; Piper's 200 ms intra-passage sentence pause follows Piper's documented default. These are fixed-duration hints, not model-predicted prosody. Current timings are heuristic and require listening evaluation before further tuning.

The default CLI uses `build_narration_plan()` and synthesizes each unit separately. It persists each mapped WAV atomically and writes a schema 2 manifest: per-passage source span, unit id, pause and duration, plus `total_units`, `completed_units` and `complete`. The desktop player reads that manifest, loads the chunks sequentially, translates a global seek position into segment plus local time, applies the playback rate, inserts per-unit pause timers, and offers retry/skip after a chunk load error. The explicit executable override remains one-shot and exposes its combined WAV as one playback segment.

The Piper worker passes `None` for `noise_scale` and `noise_w_scale` by default so Piper applies values from the selected voice's JSON config. Optional `less` and `more` profiles scale those per-voice values to 0.85× and 1.10× respectively (capped at 1.0); they are experiments in synthesis variation, not pitch or emotion controls. The current default remains the voice configuration. `listening_eval.py` creates randomized, RMS-matched participant packs across an eight-passage corpus and keeps the mapping key in a separate facilitator directory. No quality conclusion is implied until listeners submit ratings.

## Phase 5 desktop shell

`src-tauri/` is a Tauri 2.10.3 Rust application with a React and TypeScript frontend in `ui-react/`. Rust invokes the platform's native document picker (Zenity/Kdialog on Linux, AppleScript on macOS, and PowerShell on Windows), validates supported file extensions, and stores the canonical path in managed state. The frontend cannot submit arbitrary source paths or call filesystem APIs. Rust invokes the existing Python CLI with safe argument boundaries and a minimal inherited environment, writes generated audio beneath the per-user app-local-data directory, tracks the Python process, kills its process tree on cancellation/window close, and emits a completion event after validating the generated manifest and chunk paths.

Process trees (`src-tauri/src/process_tree.rs`): every Python worker (synthesis, narration preview, LLM) is built by `worker_command`, which clears the environment and passes through an allowlist (`HOME`, locale, temp and cache directories; proxy and CA-bundle variables only for the LLM worker, which may reach a remote provider). On Unix a worker leads its own process group, and stopping it signals the group. On Windows the worker is assigned to a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. Terminating the job stops the whole tree, and if Sonara itself dies the OS closes the handle and kills the tree. Workers also get `SONARA_PARENT_WATCH=1`: `parent_watch.py` polls the parent PID once a second, and when Sonara is gone (for example a crash under `panic = "abort"`) it kills the worker's process group, or exits on platforms without one.

Read-along: each manifest chunk records its source block ID and character offsets within the block. Rust validates those (`SourceSpan`) and passes them in the frontend session. `get_reader_document` returns the blocks of `extracted_document.json` only when its hash is the open session's. The reading view maps the playing passage to its block and highlights the span; offsets are code points and are converted for JavaScript strings.

The Rust core returns session metadata and a local media URL base to the frontend, but no filesystem paths. To avoid WebKit rejecting WAVs served over a custom media scheme, Rust owns an ephemeral HTTP listener bound only to `127.0.0.1`. It accepts a random per-launch token and an active-session document hash/passage index, verifies the exact Host header and canonical path under the session's own `sessions/<run-id>/chunks/`, and supports bounded byte ranges. The CSP allows the listener as a media source only; the listener shuts down with the window. Reader progress is JSON version 2 (segment plus narration `unitId`), atomically written once per second and on controls under app-local-data, keyed by source SHA-256. Each synthesis run writes to its own directory, and the session named by `current-session` is restored on launch if all its chunks still exist. The layout and the 1.x upgrade are described in [Configuration](CONFIGURATION.md#desktop-data-layout). SQLite is deferred because this prototype has one active session and one small progress record per document.

The Linux Cargo build and Rust unit tests pass. A user reported WebKit media error 4 for the former custom URI audio source; the desktop player now uses the token-scoped loopback HTTP listener. The new playback path awaits a graphical retest. This execution environment cannot connect to its advertised display sockets, so the window and audible playback cannot be launched here. Native picker implementations exist for Linux, macOS, and Windows, but only Linux is currently exercised. Tauri installer bundling is disabled; Python, ONNX Runtime, and model files remain external prerequisites.

## Component boundaries and current scope

- Rust/Tauri: current one-window application lifecycle, selected-document orchestration, child process cancellation, range-limited local audio serving, JSON progress persistence, and native file picking implementations for Linux, macOS, and Windows. The pickers are implemented, but only Linux has been exercised in this environment. Durable library reopening remains limited; this is not a full document-management database.
- Document adapters: PDF, DOCX, EPUB, TXT parsing into stable blocks and source locations. The current PDF adapter and schema are in Python; Rust ownership is deferred until the desktop core is introduced.
- Analysis and narration planning: `narration.py` provides deterministic segmentation, structure-aware pause metadata, and reversible spoken-text changes without rewriting source content; preview and synthesis consume the same source-mapped plan.
- TTS adapter: `tts_engine.py` defines capability/audio/chunk contracts. The default Piper adapter runs `piper_worker.py` as one persistent local process per session. JSON-line requests carry text over stdin; audio stays in bounded, temporary WAV chunk files. Cancellation terminates the worker process, including in-flight inference. The CLI cache is keyed by source hash, planner/schema version, runtime/model/config hashes, voice, speed, unit ID and source/spoken text. LRU cleanup removes inactive hash WAVs toward a 512 MiB budget; current-plan entries are protected and may temporarily exceed it.
- Audio: synthesis uses bounded prefetch and temporary chunks; the desktop shell schedules persisted mapped WAVs with a single audio element. The desktop's loopback HTTP server handles each connection on its own thread (at most 8 at once) and streams the requested range from disk. This avoids holding the whole document's PCM in the frontend, but does not provide native device controls. The CLI also writes a combined WAV; the desktop app does not.
- Streaming playback: listening starts after the first passage. Python rewrites the run's `audio_chunks.json` after every passage (`complete: false`, with `completed_units`/`total_units`), and each WAV is in place before the manifest names it. The Rust monitor polls it every 150 ms. It validates only the new passages, keeps them in a streaming session the audio server serves from, and sends them in `synthesis-progress`: the first event carries the session so far, and later events carry only new passages from `firstChunk`. If the frontend sees a gap, it catches up with `streaming_session`. While a document streams, its audio comes only from the new run, never from an older run of the same document. The player waits ("Preparing passage N…") rather than ending when it reaches a passage that is not ready, and holds a saved position until that passage exists. Seeking is limited to the ready passages, and the total length is shown as an estimate. `synthesis-finished` completes the session in place without moving the listener. Cancelling a streaming run discards it and reopens the session that was open before. Python handles SIGTERM by unwinding, so the engine worker closes and uncommitted chunks are removed.
- React/TypeScript: listening workspace, player, recent-document history, and settings. The UI requests desktop capabilities through explicit Tauri commands rather than arbitrary filesystem access. A durable, searchable library with document reopening remains future work.
- Python: primary document-processing, narration-planning, and local TTS worker runtime. A separate worker also hosts optional LLM integrations. The optional `llama-cpp-python` binding is not part of the default Piper requirements.

## Data and ownership

The original file remains user-owned and is read-only to the pipeline. Extracted text is derived data; audio is a regenerable cache. Current block IDs hash page, global order, top-left source position, and block text, making IDs repeatable for the same extraction. Source boxes include page dimensions and point coordinates. JSON serialization is available from the document object but the CLI does not yet persist it. The prototype stores audio and player HTML in the caller-selected output directory and playback position in browser-local storage.

## Errors and cancellation

Poppler extraction has a 100 MiB input limit, 32 MiB stdout cap, 1 MiB stderr cap, and 60-second timeout; failures are actionable and partial extraction output is not passed to TTS. The persistent Piper worker has a model-load timeout, per-unit synthesis timeout, structured errors, and explicit termination on stream cancellation or application close. Its stdin carries request text, while paths/metadata are the only protocol arguments. The compatibility executable override uses a temporary UTF-8 input file rather than putting document text in argv. Inference runs outside any real-time audio callback.

## Known limits

The desktop app supports PDF, TXT/TEXT, Markdown, DOCX, and EPUB; optional OCR applies to scanned PDFs when Tesseract and Poppler are installed. A library database, native audio-device playback and voice cloning are not implemented; highlighting is passage-level, not word-level. Narration rules are finite and heuristic. The CLI creates mapped chunks and a combined WAV; it has no player. Cache cleanup is limited to inactive cache files; active-plan entries may temporarily exceed the configured budget. Poppler's bbox layout does not encode reliable semantic table/heading structure; category labels are heuristics and multi-column/table-like order can remain ambiguous. PyMuPDF has not been installed or benchmarked. Piper 1.8.0, ONNX Runtime 1.31.0, and the John medium voice are installed locally. PDF corpus extraction and end-to-end synthesis pass. The Tauri desktop window still needs interactive validation in a graphical environment.

## Embedded LLM worker

## Resource policy

The settings UI offers Low resource, Standard, and High performance policies. The selected value is passed to the existing Python reading process. It changes TTS prefetch depth (1, 2, or 4 chunks) and the inactive audio WAV cache budget (128 MiB, 512 MiB, or 1 GiB); active narration-plan cache entries remain protected and can temporarily exceed the budget. It does not select another model or voice. High performance increases local TTS prefetch only; it does not enable parallel model inference. No hardware headroom check is used, and low-resource policy does not currently rewrite the LLM context setting.

Legacy llama.cpp HTTP embeddings are requested one passage at a time. Their content-addressed JSON cache is capped at 256 MiB by default and can be configured with `SONARA_EMBEDDING_CACHE_MAX_BYTES`; inactive entries are pruned LRU. This cache currently lives at Sonara's cache directory and cache invalidation is tied to endpoint, embedding model, input schema, and document content. Sonara's HTTP client cannot set an externally managed server's context length, slot count, or thread count. The existing client context setting applies only to embedded llama-cpp-python; server launch settings remain user-managed. The external server owns its own memory and lifecycle.

The Tauri `AppState` owns one lazily started `llm_client.py worker` child and serializes bounded newline-delimited JSON request/response messages through its stdin/stdout pipes. Prompts and credentials are never placed in process arguments or worker logs. The worker starts on the first LLM IPC call, but does not initialize a model until an embedded generation action needs one. App close sends a shutdown action. If the app is forcibly terminated, the parent watch (and on Windows the Job Object) stops the worker.

Assistant retrieval (`retrieval.py`): Rust names the open document to the worker (the session's `extracted_document.json`, else the selected file, which is extracted); the webview never sends document text. `chunk_blocks` builds passages of up to 1,200 characters from its blocks, merging short blocks on the same page and splitting long ones at sentence ends. Each passage keeps its pieces as `(block id, start, end)` code-point offsets and its page. After an answer, the `[Passage n]` labels it uses are matched against the passages that were sent; matches become citations (passage, page, spans, excerpt) and other labels are dropped. The drawer shows citations as page chips, and the reading view scrolls to and highlights the cited span. `chunk_document` keeps the plain-text split for the retrieval evaluation. A document that fits the context budget is sent whole, labelled by passage. Otherwise BM25 ranks passages for every provider, on the device. With the HTTP llama.cpp provider and its embedding endpoint, a cached vector index ranks them too, and the two rankings are combined by reciprocal rank fusion; if embeddings fail, BM25 is used alone. The best passages that fit the budget are sent in document order with stable `[Passage n]` labels. The budget is 6,000 characters, smaller for an embedded model whose context window is small. Summaries of documents over the budget are map-reduce: up to 8 windows spread across the document are summarised, then combined, within 240 s so the reply fits the 300 s RPC limit.

`embedded_llama_cpp` is a direct provider implemented with the optional `llama-cpp-python` package. Its single `EmbeddedModelManager` validates the configured GGUF, imports `Llama` lazily, lets the library use chat-template metadata stored in the model, serializes inference, reuses the same instance for matching model/runtime settings, and closes it after the configured idle timeout. Changing model path, context, threads, or batch settings unloads the previous instance before loading the new configuration. A timer cannot unload while inference holds the manager lock. `UNLOADED` means its close path ran; it does not guarantee that the operating system has reclaimed every mapped or cached page.

Assistant requests can be stopped: `llm_cancel` kills the busy worker through its side handle (as shutdown does), and the waiting call reports "The request was stopped." The next request starts a new worker.

The provider `llama_cpp` continues to mean a loopback OpenAI-compatible HTTP server. In the managed mode (`managedServer`), `llm_server.rs` runs and supervises `llama-server` itself, and Rust fills in the chat and embedding endpoints of each request; see CONFIGURATION.md, "Managed llama-server". It is intentionally not auto-migrated. Ollama, OpenAI, Gemini, and custom OpenAI-compatible providers continue through the same `chat_completion` abstraction. Embedded mode never falls back to a server or cloud provider. It currently uses bounded direct document context rather than vector retrieval; the previous HTTP embeddings path remains limited to the legacy llama.cpp server. Sonara does not infer embedding capability from a chat GGUF.

The model path may be selected directly or discovered as a top-level `.gguf` file in a configured directory and Sonara's limited user model directories. Sonara does not search arbitrary filesystem paths or download models. Local requests are serialized. Each reply has a 300-second limit; a worker that exceeds it, or returns malformed or oversized output, is killed and replaced on the next request. Active-request cancellation is not exposed, but closing the app does not wait for an in-flight request: it kills a busy worker directly and gives an idle one three seconds to unload its model.
